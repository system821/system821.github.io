SpringCloud 框架技术

基础知识

负载均衡

基本概念

LoadBalancer 解决的是：在客户端（调用方）决定请求哪个服务实例

负载均衡在系统架构中是一个非常重要并且不得不去实现的内容。因为负载均衡是使系统高可用、缓解网络压力和扩容处理能力的重要手段之一。通常所说的负载均衡指的是服务端负载均衡，其中分为硬件负载均衡和软件负载均衡。硬件负载均衡主要通过在服务器节点之间安装专门用于负载均衡的设备来实现，比如F5等；而软件负载均衡则通过在服务器上安装一些具有负载均衡功能或模块的软件来实现，比如Nginx等

服务负载均衡

[客户端] —–> [负载均衡器] —–> 【各个服务节点】

客户端发送请求到负载均衡器(Load Balancer, LB)，然后这台负载均衡器负责将接收到的各个请求转发到运行中的某个服务节点上，接收到请求的服务节点做响应处理
负载均衡器运行在一台独立的服务器上并充当代理(Proxy)。所有的请求都需要通过负载均衡器的转发才能实现服务调用，这可能会是一个问题，因为当服务请求量越来越大时，负载均衡器将会成为系统的瓶颈。同时，一旦负载均衡器自身发生失败，整个微服务的调用过程都将发生失败。因此，为了避免集中式负载均衡所带来的这种问题，采用客户端负载均衡，这同样是一种常用的实现方式。

客户端负载均衡
简单来说，客户端负载均衡就是在客户端程序内部设定一个调度算法，在向服务器发起请求时，先执行调度算法计算出目标服务器地址。
与服务端负载均衡相比，客户端负载均衡不需要架设专门的服务端代理。如果客户端应用程序能够获取服务列表，并具备成熟的调度算法，就可以对外提供相关的API，从而成为一种独立的工具和框架。在微服务架构的实现框架中，客户端负载均衡是常见的负载均衡实现方案，包括Dubbo和Spring Cloud/Spring Cloud Alibaba在内的很多框架采用的都是客户端负载均衡机制

负载均衡算法
1.静态负载均衡算法
(1)随机算法
(2)轮询算法
2.动态负载均衡算法
(1)最少连接数算法
(2)服务调用时延算法
(3)源IP哈希算法

整体流程

负载均衡整体流程：

order-service 发起调用 user-service
▼

OpenFeign 拦截请求，发现服务名 “user-service”
▼

LoadBalancer 从 Nacos 拉取 “user-service” 的所有实例列表
▼

LoadBalancer 根据策略（默认轮询）选择一个实例
▼

将 “user-service” 替换为真实 IP:Port，发起 HTTP 请求

LoadBalancer跟OpenFeign关系：

LoadBalancer 的作用：从 Nacos 拿到一堆服务实例，按一定策略（轮询/随机等）帮你挑一个，把服务名换成真实地址，完成调用。
它和 OpenFeign 是搭档关系：
OpenFeign：负责声明式 HTTP 调用（像调用本地方法一样调用远程接口）
LoadBalancer：负责选择具体调用哪个实例（负载均衡）
两者结合，你写代码时完全感知不到远程调用和负载均衡的存在，就像调用本地方法一样简单

Ribbon

Ribbon

Spring Cloud Ribbon是一个基于HTTP和TCP的客户端负载均衡工具，它基于Netflix Ribbon实现。通过Spring Cloud的封装，可以让使用者轻松地将面向服务的REST模板请求自动转换成客户端负载均衡的服务调用。

Ribbon主要有以下三大子模块：

(1)Ribbon-Core: 该模块为Ribbon的核心，主要包括负载均衡器接口定义、客户端接口定义、内置的负载均衡实现等API

(2)Ribbon-Eureka: 该模块为Eureka客户端提供负载均衡实现类

(3)Ribbon-HttpClient:该模块提供含有负载均衡功能的REST客户端，用于对Apache的HttpClient进行封装

Ribbon的两个主要作用：

(1)基于Ribbon实现服务调用，是通过拉取到的所有服务列表组成（服务名称请求路径的）映射关系，借助RestTemplate最终实现的。

(2)当有多个服务提供者时，Ribbon可以根据负载均衡的算法自动选择需要调用的服务地址。

90% 的情况下，Ribbon 是”空气”——你在用 Feign 或 @LoadBalanced RestTemplate 时，它自动干活，你无感知。

只有 10% 的情况下需要显式配置——当你对负载均衡有特殊需求（灰度、权重、机房路由）时，才需要动手改 Ribbon 的规则。

Nginx和Ribbon区别：

Nginx 和 Ribbon/Spring Cloud LoadBalancer 都负责负载均衡，但它们工作的位置和侧重点完全不同。

  • Nginx 是服务端负载均衡（也叫集中式负载均衡）。请求先打到 Nginx，由 Nginx 决定转发给哪个后端服务器。
  • Ribbon/Spring Cloud LoadBalancer 是客户端负载均衡（也叫软负载）。调用方知道自己要调谁，自己从注册中心查列表，自己决定发给哪个实例。

SpirngCloud Gateway

基本概念

服务网关：请求管理，路由规则，日志记录，安全管理，访问控制，服务适配，过滤器，网关限流

作为系统访问的唯一入口，服务网关是一种服务端应用。从设计模式上讲，我们也可以把服务网关看作外观(Facade)模式的一种具体表现形式。外观模式的作用就是把复杂度屏蔽在系统内部，从而缓解耦合，在微服务架构中，服务网关的核心要点在于，所有的客户端和第三方服务都通过统一的网关接入到微服务系统，并在网关层处理所有的非业务功能。服务网关的作用体现在解耦、API优化和简化调用过程等主要方面。

Spring Cloud Gateway组件Spring Cloud Gateway中的核心组件有三个，分别是路由(Route)、**谓词(Predicate)**和 过滤器(Filter)。

(1) 路由路由是网关最基础的部分，路由信息由一个ID，一个目标URL、一组断言工厂和一组过滤器组成。如果断言为真，则说明请求URL和配置的路由匹配

(2) 谓词Spring Cloud Gateway中的谓词函数允许开发者去定义匹配来自HTTP请求的任何信息，比如请求头和参数等，符合谓词规则的请求才能通过。而所谓谓词，本质上是一种判断条件，用于将HTTP请求与路由进行匹配。Spring Cloud Gateway内置了大量的谓词组件，可以分别对HTTP请求的消息头、请求路径等常见的路由媒介进行自动匹配以便决定路由结果

(3) 过滤器一个标准的Spring WebFilter, Spring Cloud Gateway中的Filter分为两种类型，即 Gateway Filter和 Global Filter。 过滤器可以对请求处理过程进行拦截，从而添加定制化处理机制。Spring Cloud Gateway中的过滤器和Zuul等其他框架中的过滤器是同一个概念，都可以用于响应HTTP请求之前或之后修改请求本身及对应的响应结果，区别在于两者的类型和实现方式不同。

工作流程

管道-过滤器架构模式

管道-过滤器在结构上是一种组合行为，通常以切面(Aspect)的方式在主流程上添加定制化组件。当我们在阅读一些开源框架代码时，看到Filter（过滤器）或Interceptor（拦截器）等名词时，往往就是碰上了管道-过滤器模式

Spring MVC模式

请求到达 → ServletRequest → 过滤器链 → DispatcherServlet → 遍历 HandlerMapping → 找到匹配的 Handler → 通过 HandlerAdapter 执行 → 返回响应

DispatcherServlet 拿着请求，挨个问 HandlerMapping“谁能处理这个 URL”，找到后交给 HandlerAdapter 去干活。

Spring WebFlux模式（响应式Web框架）

请求 → Reactive 服务器 → WebFilterChain → DispatcherHandler → HandlerMapping → HandlerAdapter → 处理器（Controller / RouterFunction） → 返回 Mono/Flux

Spring MVC 与 Spring WebFlux 对比：

维度 Spring MVC Spring WebFlux
底层 API Servlet API（阻塞 I/O） Reactive Streams（非阻塞 I/O）
容器 Servlet 容器（Tomcat、Jetty、Undertow） 响应式容器（Netty、Jetty 响应式、Servlet 3.1+ 容器）
线程模型 每个请求一个线程（线程池），线程阻塞等待 少量固定线程（如 Netty 事件循环），非阻塞
并发能力 受线程池大小限制，适合 CPU 密集型或中等 I/O 极高，适合 I/O 密集、长连接、高并发场景
前端控制器 DispatcherServlet（继承 HttpServlet） DispatcherHandler（不是 Servlet）
请求入口 Servlet 容器 → 过滤器链 → DispatcherServlet Reactive 服务器 → WebFilterChain → DispatcherHandler
映射处理器 (HandlerMapping) BeanNameUrlHandlerMapping RequestMappingHandlerMapping RequestMappingHandlerMapping RouterFunctionMapping
适配器 (HandlerAdapter) RequestMappingHandlerAdapter 等 RequestMappingHandlerAdapter HandlerFunctionAdapter
处理器 (Handler) @Controller + @RequestMapping 方法 @Controller + @RequestMapping 方法 或 RouterFunction（函数式）
返回值 ModelAndView、String、ResponseEntity 等 Mono、Flux、Mono<ServerResponse> 等
适用场景 传统 Web 应用、RESTful API（非极端高并发） 高并发、长连接、流式响应、网关、微服务边缘服务
学习曲线 相对平缓 需要理解响应式编程（Reactor、背压等）

执行流程

客户端 ▶ DispatcherHandler 【WebFlux 前端控制器（网关中也用它】 ▶ RoutePredicateHandlerMapping【根据断言（Predicate）匹配路由】(断言失败 → 无法匹配路由，返回错误/404 | 断言成功 ▶ lookupRoute（找到匹配的路由定义） ▶ FilteringWebHandler 获取该路由关联的过滤器链) ▶ Filter → Filter → Filter ← 依次执行（前置/后置逻辑）▶ 目标服务

组件 作用
DispatcherHandler WebFlux 统一入口，分发请求
RoutePredicateHandlerMapping 核心路由匹配器，用断言（如 Path=/api/**、Method=GET）判断是否匹配某路由
lookupRoute 断言成功后，获取匹配的路由定义（含目标 URI + 过滤器列表）
FilteringWebHandler 执行该路由下的所有 GatewayFilter（类似局部过滤器链）
Filter 链 依次执行过滤器（可做鉴权、日志、重试、限流等），最后转发到目标服务

请求进入 DispatcherHandler → 通过 RoutePredicateHandlerMapping 逐一断言匹配路由 → 找到后取出路由关联的过滤器链 → 依次执行过滤器 → 转发到目标服务

这本质上是一个 “断言匹配 + 过滤器链 + 代理转发” 的网关处理模型

Spring Cloud Gateway的核心功能就是请求路由和转发，而围绕这一核心功能，开发人员可以做的事情有很多，比如实现对服务的灰度发布、实现对请求的拦截并添加异常处理机制、实现对请求的限流降级等

过滤器

在Spring Cloud Gateway中内置了许多过滤器，这些过滤器可以分成两大类，即GatewayFilter和GlobalFilter，正如我们在FilteringWebHandler中所看到的。其中，GatewayFilter通过配置作用于每个路由，而GlobalFilter则作用于所有的请求。当请求匹配到对应路由时，会将GlobalFilter和已绑定路由的GatewayFilter合并到一起。所有的过滤器都实现了org.springframework.core.Ordered接口，因此会根据过滤器的Order值进行排序

局部过滤器

局部过滤器可以对访问的url进行过滤和切面处理

全局过滤器 <鉴权逻辑>

全局过滤器(GlobalFilter)作用于所有路由，Spring Cloud Gateway定义了GlobalFilter接口，用户可以自定义实现自己的全局过滤器。通过全局过滤器可以实现对权限的统一校验、安全性验证等功能，并且全局过滤器也是程序员使用比较多的过滤器

LoadBalance —> LoadBalanceClientFilter

HttpClient —> NettyRoutingFilter/NettyWriteResponseFilter

Websocket —> WebsocketRoutingFilter

ForwardPath —> ForwardPathFilter

RouteToRequestUrl —>RouteToRequestUrlFilter

WebClient —> WebClientHttpRoutingFilter/WebClientWriteResponseFilter
